# WooCommerce y primer informe PDF

WooCommerce es el primer adaptador de ventas priorizado. En Integraciones, un administrador puede guardar la URL HTTPS de la tienda y una clave de consumidor con permisos **solo de lectura**, y usar **Probar conexión**. La prueba consulta únicamente `GET /wp-json/wc/v3/orders?per_page=1&page=1`; no importa pedidos ni marca ventas como sincronizadas. No se siguen redirecciones que pudieran reenviar la cabecera de autorización.

Cualquier usuario autenticado (administrador o viewer) puede consultar una **vista previa** por integración y fechas de compra desde Ventas: `GET /api/integrations/:id/woocommerce/sales-preview?from=AAAA-MM-DD&to=AAAA-MM-DD`. Usa la ventana local de la tienda (`after`/`before`, `dates_are_gmt=false`), máximo 31 días y cinco páginas de 100 pedidos; si se supera el límite, falla sin mostrar un total parcial. Reintenta de forma acotada errores transitorios/429, pero no errores de credenciales. Devuelve solo agregados por fecha y moneda, sin PII, no se persiste y no modifica el estado de sincronización.

La pestaña **Ventas** permite consultar un periodo limitado con desglose de pedidos completados, importes brutos, reembolsos y venta final por fecha/moneda. Los administradores sincronizan y guardan snapshots completos; viewers leen primero el snapshot exacto y, si no existe, realizan una vista previa que no se persiste. Solo los datos completos se guardan.

Las pestañas **Tráfico/Ads** y los KPI de **RRSS** tampoco derivan inversión, ROAS, sesiones, seguidores o interacción de ventas u otras señales no relacionadas. Tráfico muestra la ausencia de una fuente publicitaria real; RRSS conserva su plan editable local y omite el panel de rendimiento social hasta conectar un proveedor.

La pestaña **SEO** permanece como estado no disponible (sin proveedor Search Console): no genera consultas, clics, posiciones ni recomendaciones de optimización ficticias.

El lector preparado en `src/lib/woocommerce.ts` admite rangos de modificación GMT, paginación acotada y extrae solo ID, estado, moneda, importes, fechas y los importes/ID de reembolsos. Descarta datos personales del pedido y motivos de reembolso. La regla confirmada para ventas es **solo pedidos `completed`**, con **IVA y envío incluidos**: se suma `total` (el importe final del pedido), sin añadir de nuevo `total_tax` ni `shipping_total`. La venta se atribuye **siempre al día de compra** (`date_created` de WooCommerce en la zona horaria de la tienda), aunque se complete o reembolse después. La política de reembolsos se edita en la integración WooCommerce de cada cliente: por defecto **restar**, o **no restar** para evitar duplicidad con sus propias cuentas. `summarizeCompletedOrderSales` devuelve bruto, reembolsos y venta según esa política, separados por fecha y moneda; deduplica por ID conservando la última modificación. Un pedido cuyo estado final ya no sea `completed` queda fuera incluso con la opción «no restar». Siguiendo la API v3 de WooCommerce, `total`, `total_tax`, `shipping_total`, `date_created` y la lista de `refunds` son datos de origen de solo lectura: las correcciones se hacen en WooCommerce; Infidash no emite PUT/POST/DELETE sobre pedidos o reembolsos. Las sincronizaciones se guardan de forma atómica por integración, hash de tienda HTTPS y ventana exacta de compra; almacenan únicamente campos del pedido necesarios para agregados (sin PII ni credenciales), y calculan la política de reembolsos al leer para admitir cambios por cliente. La coincidencia con tienda real y las monedas aún requieren conciliación en staging. Nunca introduzcas claves reales en pruebas o documentación.

La pestaña Reportes ya permite descargar un **PDF autenticado** por cliente y periodo (hasta 367 días) con las métricas diarias existentes. Muestra fuente, cobertura de días y que sus importes **no están conciliados con WooCommerce**. Un día sin registro no cuenta como cero. El histórico visible ya no se corta a seis filas. El PDF no se guarda como ejecución persistente y no incorpora todavía envío, enlaces compartidos, programación ni Notion; esas partes de la fase 5 siguen pendientes.

Pruebas locales seguras: `npm run test:unit`, `npm run lint`, `npm run build`. `npm run test:db` y `npm run test:api` requieren el PostgreSQL desechable configurado en `docs/testing.md` antes de habilitar una integración real.
