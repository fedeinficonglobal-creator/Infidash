# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. Follow `AGENTS.md` for the concise repository-wide contributor guidance; this file carries the deeper architecture and operational history.

## What this is

Infidash: a marketing agency dashboard (React + Fastify) for tracking clients, sales, traffic, SEO, RRSS (social), deterministic rule-based insights, reports, integrations, and an editorial "Contenidos" module that dispatches content-generation/publishing jobs to n8n workflows. Auth is local (email/password, sessions), with `admin`/`viewer` roles. UI copy and API error messages are in Spanish.

## Commands

```bash
npm run dev              # Vite frontend on http://127.0.0.1:3000 (proxies /api -> :4000)
npm run api              # Fastify API on http://127.0.0.1:4000 (alias: npm run dev:api / npm start)
npm run build             # production build (vite build)
npm run preview           # preview the build
npm run lint              # tsc --noEmit for both tsconfig.json and tsconfig.node.json (no separate linter)
npm test                   # safe unit and contract suites (run-tests.mjs defaults to the `unit` suite)
npm run db:migrate:editorial   # apply pending migrations (core `_core_` first, then editorial; advisory lock + checksum)
npm run db:backup         # take a gzip pg_dump now (+ retention); --label=x, --no-retention
npm run postiz:cleanup    # dry-run: expired Postiz media files; --apply deletes, --check-disk alerts on disk usage
npm run leads:erase       # dry-run: leads of one email (--email=); --apply deletes (GDPR requests)
npm run content:import    # dry-run import of a Content Hub export; add -- --apply to write
npm run clean             # rm -rf dist/ and server.js (does not touch data/)
```

Run the frontend and API in two separate terminals during development (`npm run dev` + `npm run api`). `DATABASE_URL` must be set (via `.env`/`.env.local`, copy from `.env.example`) — the app refuses to start without it; other env vars (`API_PORT`/`PORT`, `DATABASE_SSL`, `APP_URL`, `EDITORIAL_DB_POOL_MAX`/`..._IDLE_TIMEOUT_MS`/`..._CONNECTION_TIMEOUT_MS`, `CORE_DB_POOL_MAX`) are documented in `.env.example` and `README.md`. Newer opt-in/operational variables are documented only in `README.md` (`.env.example` is not edited by remediation PRs): `INFIDASH_TRUST_PROXY` (set to `1` behind EasyPanel/Traefik), `INFIDASH_CSP_MODE` (`report-only` default | `enforce` | `off`), `INFIDASH_ALLOW_PRIVATE_URLS=1` (dev override of the SSRF guard), `LOG_LEVEL`, `INFIDASH_CREDENTIALS_KEY`/`..._PREVIOUS`, `INFIDASH_BACKUP_DIR`/`INFIDASH_BACKUP_SCHEDULE_HOUR`/`BACKUP_KEEP_DAILY`/`BACKUP_KEEP_WEEKLY`, `POSTIZ_UPLOAD_DIR`/`POSTIZ_UPLOAD_URL_PREFIX`/`POSTIZ_MEDIA_RETENTION_DAYS`, `INFIDASH_MAX_CONCURRENT_UPLOADS`/`INFIDASH_UPLOAD_TMP_DIR`, `LEADS_RETENTION_MONTHS`/`LEADS_RAW_PAYLOAD_DAYS`, `METRICS_FAILED_JOBS_WARN`.

Run one safe file with `npx tsx --test tests/<name>.test.ts`. Do not run the DB/API files this way — the db files (`tests/monthly-model.test.ts`, `tests/client-memberships.test.ts`, every `tests/core-characterization.*.test.ts`, `tests/secret-box.db.test.ts`, `tests/core-baseline-migration.db.test.ts`, ...) and `tests/api-regression.test.ts` (api) are routed through `scripts/run-tests.mjs` (`databaseFiles`), which enforces the disposable-database guard and gives the child processes a throwaway `INFIDASH_CREDENTIALS_KEY`; invoking them directly bypasses it (they start with `import './helpers/isolated-harness-required.js'` and throw). A new db test must be added to `databaseFiles` in `scripts/run-tests.mjs` and to the guard lists in `tests/test-runner.test.ts` (names starting with `core-characterization.` are picked up automatically). There is no local PostgreSQL/Docker on the dev machine: db/api tests only run in CI. `npm test` and `npm run test:unit` run the guarded safe suite; `npm run test:db` runs DB-mutating tests and `npm run test:api` starts an isolated API before HTTP regressions. Both require `INFIDASH_TEST_DATABASE_URL` for a disposable loopback PostgreSQL database with a distinct `test` name segment; API tests also require loopback `INFIDASH_TEST_API_BASE_URL`. Never use shared, staging, or production data. See `docs/testing.md`. The API and database suites are separate from `npm test`.

CI (`.github/workflows/ci.yml`, Node 24, 12-minute job timeouts) has four jobs: `safe-checks` (blocking `npm audit --audit-level=high`, lint, `npm test`, build, then `tests/bundle-budget.test.ts` against the fresh build), `database-tests` (`npm run test:db` on PostgreSQL 16, then `db:migrate:editorial` twice to prove idempotency), `api-tests` (`npm run build` + `npm run test:api`) and `docker-build` (builds the production image and smoke-checks it: Node 24, `tsx` and `pg_dump` 17 present, no compilers/devDependencies). A change is done when all pass. `.github/workflows/deploy.yml` is an opt-in CD workflow (see Deployment). Workflow: one PR = one concern, Conventional Commits, merge commits after green CI; never edit an applied migration (checksums).

## Architecture

### Two separate pg pools to the same Postgres database

Both data layers are **async `pg.Pool`s** over the same `DATABASE_URL`; keep them separate and match the pattern of the module you extend:

1. **Core app data** (`src/lib/database.ts` + `src/lib/corePool.ts`): users, sessions, clients, daily stats, integrations and provider snapshots, UX snapshots, report runs, RRSS channels, monthly KPIs, leads. Every function is `async` and takes an optional trailing `db: CoreQueryable = getCoreDb()` (tests pass a fake). Use `coreAll`/`coreGet`/`coreRun` with **`$n` bind parameters only** (never interpolate values); cast where Postgres cannot infer the type (`$n::numeric` for fractional values bound to INTEGER columns, `$n::date`, `$n::timestamptz`, `$n::jsonb`, `COUNT(*)::int`). Multi-statement atomicity uses `withCoreTransaction`. Integrity errors (23502/23503/23505/23514) are re-wrapped by `mapCorePgError` into the `ERROR:  …` message shape. The core pool has its own type parsers: **DATE comes back as a plain `YYYY-MM-DD` string and TIMESTAMPTZ as a fixed-width ISO `…sssZ` string** (the API/JSON contract is strings everywhere); `NUMERIC`/`int8` would come back as strings. `getCoreDb()` waits for `initializeCoreDatabase()` (memoized: applies core migrations, then under an advisory lock runs seed, membership backfill, integration normalization, credentials encryption, legacy import) so any process importing `database.ts` gets a complete schema. The old `psql`/`spawnSync` shim, `escapeSqlLiteral` and `getDatabase()` no longer exist; `grep spawnSync src server.ts` must stay empty.
2. **Editorial/content module** (`src/server/content/*`): its own pool (`postgres.ts`), scoped to the `editorial` schema, with repository classes.

**Migrations** live in `db/migrations/*.sql` and are applied by `runEditorialMigrations`/`runCoreMigrations` (`src/server/content/migrations.ts`: advisory lock 4790321771, sha256 checksums, one transaction each, recorded in `public.schema_migrations`) at boot, from `npm run db:migrate:editorial` and in CI. Core migrations are named `NNNN_core_*.sql` and always run before editorial ones (editorial FKs point at core tables). Current set: `0004_core_baseline` (the whole core schema, idempotent), `0005_core_drop_ai_insights`, `0006_core_daily_stats_date` (stat_date TEXT→DATE; duplicate spellings keep the latest row, unparseable values go to `daily_stats_invalid_dates`), `0007_core_timestamptz_sessions_leads` (sessions.expires_at, leads.received_at → TIMESTAMPTZ; unreadable sessions deleted, leads never; originals in `leads_received_at_fallbacks`), plus editorial `0008_editorial_media_cleanup_log`. **Never edit an applied migration** (the runner refuses on checksum change; `.gitattributes` keeps `db/migrations/*.sql` LF); schema changes are always a new migration and DDL no longer lives in code. Known debt: money (`daily_stats.revenue`/`cpa`) is REAL; the NUMERIC migration (W3.2) is deferred on purpose.

### Backend structure

- `server.ts` — single Fastify entrypoint. Registers `contentRoutes` (editorial module) as a plugin, then defines all core REST routes inline (auth, users, clients, daily-stats, integrations, ux-snapshots, rrss-channels, monthly-kpis, backups, dashboard summary). Auth is a bearer/session token checked per-route via `requireSession(req, reply, roles)`; there's no global auth middleware/hook. Serves the built SPA (`dist/`) and falls back to `index.html` for non-`/api` routes in non-test mode.
- `src/lib/database.ts` — core data layer (see above) plus session/user management and the Clarity (UX analytics) sync path called from a route and from a background interval (`startClaritySyncScheduler`, first run delayed 10 s). Background schedulers (all skipped when `NODE_ENV=test`, timers unref'ed, errors logged, `pg_try_advisory_lock` where two instances must not overlap): Clarity sync, hourly session purge, KPI month close, opt-in daily backups (`src/lib/backupScheduler.ts`), daily lead retention (`src/lib/leadsRetention.ts`), per-minute metrics reporter (`src/lib/metricsReporter.ts`).
- **Cross-cutting server modules**: `src/server/security.ts` (helmet + CSP default report-only, global/login/leads rate limits, `resolveTrustProxy`: a bare number is fail-closed in Fastify 5, so a predicate/list is used), `src/lib/errorHandling.ts` + `userFacingError.ts` (only `UserFacingError` messages reach clients; anything else is logged and answered generically), `src/lib/logger.ts` (pino JSON logs with `reqId`, secret redaction incl. the lead-webhook token in URLs; health and the n8n claim poll are not logged), `src/server/health.ts` (`/api/health` shallow SELECT 1 → 503 when degraded, `?deep=1` adds migrations/core; public `/api/version` returns `startedAt` for the deploy gate), `src/lib/urlSafety.ts` (SSRF guard `assertPublicHttpUrl`/`safeFetch`: canonical host/IP checks, DNS check, manual redirect revalidation; used for admin-supplied URLs — WooCommerce, WordPress probe, Clarity), `src/lib/httpMetrics.ts` + `GET /api/admin/metrics`, `src/lib/databaseBackup.ts` + `backupRetention.ts` (gzip pg_dump via async spawn, 14 daily + 8 weekly, deletion only for names matching the backup pattern; `GET /api/admin/backups`), `src/lib/secretBox.ts` (AES-256-GCM `enc:v1:` for `integrations.credentials_json`).
- **Credentials encryption**: with `INFIDASH_CREDENTIALS_KEY` (base64, 32 bytes) every write encrypts and boot encrypts existing plaintext rows (integration id bound as AAD; `..._PREVIOUS` for rotation); without a key everything stays plaintext with one boot warning; encrypted rows with a missing/wrong key fail the boot on purpose. All reads/writes go through `encode/decodeStoredCredentials` in `database.ts`. `integrations.webhook_secret` (lead webhook token) is NOT covered.
- **Privacy**: `docs/gdpr-retention.md` is the retention/GDPR runbook (leads 24 months, raw webhook payload blanked after 90 days, `npm run leads:erase`). `deleteClient` runs in a transaction and deletes the `editorial.*` tables explicitly (several editorial FKs are RESTRICT); only internal data is deleted, already published content stays. Run `postiz:cleanup` before deleting a client (its media files are no longer referenced afterwards).
- **Postiz media cleanup**: `scripts/postiz-media-cleanup.ts` (+ `mediaRetention.ts`, `mediaCleanup.ts`) runs on the VPS against a bind-mounted uploads dir (`POSTIZ_UPLOAD_DIR`); a file is deleted only if every Infidash row referencing it is finished and older than the retention; Postiz's public API has no media delete. Creative uploads (`POST /api/social-posts/:id/media`) spool to a temp file and stream to Postiz, capped by an upload limiter (`INFIDASH_MAX_CONCURRENT_UPLOADS`).
- **WooCommerce sales**: connection testing probes the read-only WooCommerce v3 orders API. An administrator can synchronize a bounded purchase-date window (31 days / at most 500 orders); complete snapshots are keyed by integration, HTTPS store identity and exact dates. Viewers can read that exact snapshot or request a transient preview. Only `completed` orders count; `total` already includes VAT and shipping; attribution is `date_created` in the store timezone; refund handling is client-configurable and applied when aggregating; currencies are never mixed. Snapshot persistence needs PostgreSQL tests before production use.
- **Lead capture**: WordPress integrations expose a rotatable bearer webhook URL for `POST /api/public/leads/:token`. Configure Fluent Forms or Contact Form 7 to send form submissions through WP Webhooks using POST. The receiver maps common Spanish/English contact fields, supports delivery idempotency when `infidash_provider`, `infidash_form_id`, and `infidash_delivery_id` are supplied, and enforces integration disable/rotation. Authenticated lead listing is paginated/filterable and does not return the raw payload. Do not infer conversion, CPL, or pipeline value without compatible source data.
- **Integration adapter pattern** (WooCommerce → GA4 → Google Ads, in that build order — follow this shape for the next provider): a pure fetch-based client in `src/lib/<provider>.ts` (no heavy SDKs; `fetchImpl`/`getAccessToken` are injectable for tests), a `<provider>_snapshots` Postgres table plus `save<Provider>Snapshot`/`get<Provider>Snapshot` in `database.ts`, a catalog entry in `integrationCatalog.ts`, inclusion in `hasLiveIntegrationAdapter` (`integrationState.ts`) when `/test` does a real probe, and 3 REST routes per facet in `server.ts`: `<provider>/<facet>-preview` (viewer+admin, live fetch, not persisted), `<provider>/<facet>-sync` (admin-only, live fetch + persist), `<provider>/<facet>-snapshot` (viewer+admin, reads only what's persisted, degrades to `{complete:false}`). Frontend mirrors this with a service-layer client in `src/services/infidashApi.ts` and an admin-syncs/viewer-reads-snapshot-with-preview-fallback UI in the relevant `*Tab.tsx`.
  Two credential models coexist, and matching the wrong one to a new provider is the main way to get this wrong: WooCommerce and WordPress use **per-client credentials**, entered per integration via the `credentialFields` on its catalog entry and stored as JSON in `integrations.credentials_json` (encrypted at rest when `INFIDASH_CREDENTIALS_KEY` is set — see Credentials encryption; always redacted out of API responses via `secretKeys`). GA4 and Google Ads use **one shared credential for the whole agency** (a GA4 service-account JSON / a Google Ads manager-account (MCC) OAuth refresh-token set, both in server env vars only, minted into a module-level `let <provider>Service = null` at boot in `server.ts` with a `.catch()`'d immediate token-mint attempt that logs loudly instead of crashing) — per-client config is then just a non-secret ID (`propertyId`, `customerId`) that must already be linked under that shared account/property. Use the shared-credential model whenever the agency, not each client, holds the actual account (mirrors the `editorial_config`/`$env.*` split documented below for the n8n pipeline); default to per-client credentials otherwise.
- `src/lib/auth.ts`, `kpiThresholds.ts`, `integrationCatalog.ts`, `claritySync.ts`, `ga4.ts`, `googleAds.ts` — supporting logic for password hashing/session tokens, per-client KPI threshold config, the catalog of supported integration providers/capabilities, Clarity UX snapshot fetching, and the GA4/Google Ads API clients described above.
- `src/server/content/` — the editorial module, structured as its own mini-service:
  - `contracts.ts` — shared validation/enum helpers and `ContentApiError`.
  - `repository.ts` / `apiRepository.ts` — data access against the `editorial` schema.
  - `routes.ts` — Fastify plugin exposing `/api/content/*`. Supports **two distinct auth modes** on the same routes: human sessions (`resolveHumanSession`, reusing the core session token from `src/lib/database.ts`) for the dashboard UI, and scoped **service tokens** (`serviceAuth.ts`, `authenticateServiceToken`) for n8n workflows — tokens are stored only as SHA-256 hashes in `editorial.service_tokens`, scoped per-client and per-capability (e.g. `jobs:claim`, `jobs:result`, `context:read`, `events:write`).
  - `migrations.ts` — the editorial migration runner (advisory lock, checksums, transactional).
  - `importContentHub.ts` — the legacy Content Hub importer used by `scripts/import-content-hub.ts`; requires an explicit ID-mapping file (never matches clients/accounts by name) and is idempotent via `editorial.legacy_mappings`.
  - `transitions.ts` — status transition rules for content jobs.
- `db/migrations/*.sql` — core (`NNNN_core_*`) and editorial schema, the single source of truth (see Migrations above).
- `workflows/content/*.json` — sanitized, disabled n8n workflow exports: `dispatcher.v1.json`, `reconcile.v1.json`, and per-client children under `inficon-global/` (`plan`, `generate`, `publish`, `cancel`, `reschedule`). These are documentation/reference artifacts, not executed by this repo. `tests/content-workflows.test.ts` asserts the exact number of `*.v1.json` files and that each export is sanitized (`active:false`, no `pinData`, no node `credentials`, no known installation ids/secrets, every `$('Node')` reference resolves). When adding a raw n8n export, rename it to `<client>/<kind>.v1.json`, strip `credentials`, `id`, `versionId`, `meta`, `tags`, `pinData` and instance-specific `settings.errorWorkflow`, and bump the count. Job contracts are self-healing: Infidash re-reads `publications`/`publishing_accounts` (and, for `generate_content`, the plan item) server-side when a job is created or claimed rather than trusting client-submitted payloads. See `docs/content-workflows.md` and `docs/content-deployment.md` before changing job/lease/reconciliation semantics.

### Editorial/n8n pipeline: what has to be true for a job to actually run

Full diagnostics, dates and node-level history live in `docs/editorial-pipeline-history.md`; read it (plus `docs/content-workflows.md`, `docs/content-deployment.md`, `docs/editorial-recovery.md`) before debugging a workflow or changing job/lease/reconciliation semantics. Failures here are almost always **silent** in the Infidash UI. Checklist when a job seems stuck:

1. `editorial.client_settings` needs a row with `enabled = TRUE` and `workflow_bindings` (`{"generate_plan": "<n8n id>", "generate_content": …, "publish": …, "reconcile": …}`). SQL-only, no UI/API route. Missing row → 409 `EDITORIAL_DISABLED`; wrong binding → fails inside n8n (reported as `failed`, `stage: dispatcher`).
2. `editorial.publishing_accounts` needs one `active=TRUE` row per (client, provider), also SQL-only. WordPress `instance_key` is cosmetic; Postiz `external_account_id` is the real Postiz channel id sent as `integrationId`. `platform` is the content vertical (`'blog'`), **not** the social network — the network is encoded in `instance_key` (e.g. `inficonglobal-gmb`), so give each Postiz account a distinct `instance_key` containing its network name.
3. `dispatcher.v1.json` must be imported into n8n and set Active (nothing here deploys it). Trust n8n's Executions tab over a stale `$workflow.active: false`.
4. `$env.*` secrets (`INFIDASH_INTERNAL_API_URL`, `INFIDASH_SERVICE_TOKEN`, `SERPAPI_API_KEY`, `JINA_API_KEY`, `OPENAI_API_KEY`, `SERPROBOT_*`, `POSTIZ_*`, …) belong on the **n8n container**, not Infidash's `.env`, and need an n8n restart. `OPENAI_API_KEY` (raw HTTP calls) and the native n8n "OpenAi account" credential (langchain nodes) are configured separately.
5. `INFIDASH_SERVICE_TOKEN` is the raw token; only its SHA-256 (`serviceAuth.ts:hashServiceToken`) goes into `editorial.service_tokens.token_hash`.
6. «Generando» in the UI is set the instant `POST /api/content/jobs` succeeds — it is not evidence n8n is running. Ground truth: `editorial.jobs.status`/`attempt_count`/`locked_until`/`last_error`. Unstick with the admin «Marcar como fallida» button (`POST /api/content/plan-items/:id/release-generation`; refuses with 409 `JOB_IN_PROGRESS` while a live lease exists — check WordPress for an existing draft first). `createJob` refuses duplicates while an equivalent job is pending/leased/auto-retrying.
7. `plan_item` transitions are strict (`transitions.ts`): `proposed → approved → generating → review → ready`; approve before generating.
8. Each manual retry creates a **new** job row (`:new:<timestamp>` idempotency suffix), so a backlog of `failed` rows can look like one job looping. `claimJob` only reclaims `attempt_count < 8`; setting it to 8 freezes a job.
9. `409 LEASE_LOST` is usually a timing failure, not a data failure: the plan pipeline outran `Heartbeat inicial`'s `leaseSeconds` (2700), or the dispatcher's initial lease (1800) expired while Infidash was briefly unresponsive and the job was double-claimed. Check `attempt_count`/`execution_id` history.
10. Job payloads (publication, `planItem`) are rebuilt server-side on create and on **every claim** (`publicationPayloadForJob`); fixing `editorial.publications` doesn't change an already-claimed job until it is reclaimed (`UPDATE editorial.jobs SET next_attempt_at=now() …` once not `running`).

Durable rules for workflow exports and the content API:

- The `jsCode` in `workflows/content/*.json` is real code (a syntax error has shipped before); review and test it like source.
- Every failing node's error output (`onError: continueErrorOutput`) must route to a report node: `failed` before any external write, `unknown` (with `wordpressPostId`/`postizPostId` when known) once WordPress/Postiz may have been written. Optional steps (image generation/upload, featured image, plan data sources) degrade instead of failing the job. Nodes that may not have run are read via `try { $('Node') } catch`.
- Postiz network detection keys off `account.instance_key`, **never** `account.platform` (this regression has recurred; the `tests/content-workflows.test.ts` fixture varies `instance_key` with `platform` fixed at `'blog'`).
- Never bind an n8n `fixedCollection`/array parameter (e.g. Postiz `settings.setting`) with a single top-level expression — n8n iterates the string per character. Use IF branches feeding separate nodes with literal arrays (current pattern: `Es Facebook`/`Es Instagram`/`Es GMB` → 4 Postiz nodes → `Capturar respuesta/error Postiz`).
- WordPress featured images are set by a separate `POST /wp-json/wp/v2/posts/{id}` with `{"featured_media": id}` after the post is created, not via the native node's `additionalFields`. Raw HTTP nodes reuse the native WordPress credential via `predefinedCredentialType` + `wordpressApi`. The header image URL is stored in `content.seo.headerImageUrl` and reused as the default publication media.
- The GMB CTA URL is optional in the app and resolved in n8n (fallback `editorial_config.site_url`); don't add a server-side requirement without a matching UI change. The "Programar publicación" account list is `provider='postiz'` only.
- `applyContentResult` finds the existing content row by `(client_id, plan_item_id)` (the unique key), so retries create revisions rather than duplicate inserts.
- `generate.v1.json` derives `bodyText`/`excerpt` from the humanized `bodyHtml`; `applyContentResult` stores them verbatim, and the publish form defaults `copy` to `excerpt`.
- Per-client `editorial_config` supplies non-secret identifiers (`topic`, `country`, `keywords` → falls back to `topic`, `weeks_horizon`, `site_url`, `competitors`, `serprobotProjectId`, `ga4PropertyId`, `fallbackImageUrl`) read by `plan.v1.json`'s `⚙️ Configuración1`; account-wide secrets stay in n8n `$env`. Reuse this split for any multi-tenant integration.

### Frontend structure

- `src/App.tsx` — top-level shell; renders `LoginScreen` until a session exists, then `Sidebar` + one of the per-domain tab components based on `activeTabId` from `useClientStore`.
- `src/store/useClientStore.ts` (Zustand) — session bootstrap/login/logout, client list, active client/tab selection; wraps `src/services/infidashApi.ts`.
- `src/store/useContentStore.ts` (Zustand) — editorial/content state; wraps `src/services/contentApi.ts`.
- `src/services/*.ts` — API clients (`infidashApi.ts`, `contentApi.ts`, `rrssApi.ts`); `apiRequest` throws `ApiError` (with `.status`) and a 401 on an authenticated request triggers one clean logout (`sessionExpiry.ts`; login/logout paths exempt; the login screen shows «Tu sesión ha caducado»). `signal` is forwarded to `fetch`; `useClientStore` keeps a session-scoped and a client-scoped `AbortController`. Insights are deterministic rules, not generated by a model.
- `src/components/*Tab.tsx` — one component per sidebar section (Overview, Sales, Traffic, Web, SEO, Leads, RRSS, AI Insights, Reports, Integrations); `src/components/content/` holds the Contenidos tab.
- **Rules enforced by tests (source scans)**: every tab is `React.lazy` behind `Suspense`/`LazyBoundary` and the initial JS must stay < 400 KB without the `charts` chunk (`tests/bundle-budget.test.ts`, runs after the build in CI); never call a store without a selector (`use*Store(useShallow(selectX))`, named selectors in `src/store/selectors.ts`; `tests/no-whole-store-subscription.test.ts`); no `window.confirm` (use `useConfirm()`; `ConfirmProvider` is mounted in `App`); modals use the shared `Modal` (focus trap, Escape, scroll lock; no `fixed inset-0` elsewhere); no `onClick` on non-interactive elements and no `text-slate-300/400` on light backgrounds (`tests/a11y-*.test.ts`); no external fonts/`ui-avatars.com` (`@fontsource` self-hosted; `InitialsAvatar`; `tests/frontend-hygiene.test.ts`); money/number/date display goes through `src/lib/format.ts`; no tracked spreadsheets or API-key-like strings (`tests/repo-hygiene.test.ts`).
- GA4 «Tráfico»: opening the tab reads the stored snapshot, shows it, and refreshes in the background when older than 6 h (`src/lib/trafficAutoLoad.ts`; admin syncs, viewer previews); «Actualizar ahora» forces it.
- Frontend imports use explicit `.js` extensions on relative paths even though the source is `.ts`/`.tsx` (ESM `moduleResolution: bundler` convention used throughout this repo) — follow this when adding imports.
- Path alias `@/*` maps to the repo root (`tsconfig.json`, `vite.config.ts`).

### Deployment

Single multi-stage Docker image (`node:24-trixie-slim`; Debian 13 so `pg_dump` is the PostgreSQL 17 client matching production — a pg_dump older than the server refuses to dump it). Build stage: `npm ci`, `npm run build`, `npm prune --omit=dev`; runtime stage: Node + `postgresql-client` only (no compilers; `tsx` is a runtime dependency because the app runs `tsx server.ts`, which serves the API and the built SPA from one Fastify process on `PORT`/`API_PORT`, 3001 in the container). `HEALTHCHECK` hits `/api/health`. The container still runs as **root on purpose** (the `/data/backups` volume and the bind-mounted Postiz uploads are owned by root); switch to `USER node` only after checking those permissions. Production runs on EasyPanel: deploys are manual («Implementar») unless the opt-in `deploy.yml` is configured (secret `EASYPANEL_DEPLOY_URL` + variable `INFIDASH_BASE_URL`; after green CI on main it triggers the webhook and waits until `/api/version.startedAt` is newer and `/api/health?deep=1` is 200). Migrations run at container boot; rollback = `git revert` + redeploy, and type-changing migrations can only be undone by restoring a backup, so back up first (`npm run db:backup`). `INFIDASH_BACKUP_DIR` (`/data/backups`) must be a persistent volume; the Postiz uploads dir is a bind mount («montaje de enlace») of `/etc/easypanel/projects/<project>/postiz/volumes/postiz-uploads`.
