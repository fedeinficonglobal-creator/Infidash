# CLAUDE.md

This file provides Claude Code-specific architecture and operational context. Follow `AGENTS.md` for the concise repository-wide contributor guidance.

## What this is

Infidash: a marketing agency dashboard (React + Fastify) for tracking clients, sales, traffic, SEO, RRSS (social), deterministic rule-based insights, reports, integrations, and an editorial "Contenidos" module that dispatches content-generation/publishing jobs to n8n workflows. Auth is local (email/password, sessions), with `admin`/`viewer` roles. UI copy and API error messages are in Spanish.

## Commands

```bash
npm run dev              # Vite frontend on http://127.0.0.1:3000 (proxies /api -> :4000)
npm run api              # Fastify API on http://127.0.0.1:4000 (alias: npm run dev:api / npm start)
npm run build             # production build (vite build)
npm run preview           # preview the build
npm run lint              # tsc --noEmit for both tsconfig.json and tsconfig.node.json (no separate linter)
npm test                   # safe unit and contract suites (node scripts/run-tests.mjs unit)
npm run db:migrate:editorial   # apply pending `editorial` schema migrations (advisory lock + checksum)
npm run content:import    # dry-run import of a Content Hub export; add -- --apply to write
npm run clean             # rm -rf dist/ and server.js (does not touch data/)
```

Run the frontend and API in two separate terminals during development (`npm run dev` + `npm run api`). `DATABASE_URL` must be set (via `.env`/`.env.local`, copy from `.env.example`) — the app refuses to start without it; other env vars (`API_PORT`/`PORT`, `DATABASE_SSL`, `INFIDASH_BACKUP_DIR`, `APP_URL`, `EDITORIAL_DB_POOL_MAX`/`EDITORIAL_DB_IDLE_TIMEOUT_MS`/`EDITORIAL_DB_CONNECTION_TIMEOUT_MS`) are documented in `.env.example` and `README.md`.

Run one safe file with `npx tsx --test tests/<name>.test.ts`. `npm test` and `npm run test:unit` run the guarded safe suite; `npm run test:db` runs DB-mutating tests and `npm run test:api` starts an isolated API before HTTP regressions. Both require `INFIDASH_TEST_DATABASE_URL` for a disposable loopback PostgreSQL database with a distinct `test` name segment; API tests also require loopback `INFIDASH_TEST_API_BASE_URL`. Never use shared, staging, or production data. See `docs/testing.md`. The API and database suites are separate from `npm test`.

## Architecture

### Two independent persistence paths to the same Postgres database

This is the most important thing to understand before touching data code — there are **two unrelated ways the app talks to PostgreSQL**, and they must not be conflated:

1. **Core app data** (`src/lib/database.ts`, ~1800 lines): users, clients, daily stats, integrations, UX snapshots, RRSS channels, monthly KPIs. This module does **not** use a `pg` connection pool — it shells out synchronously to the `psql` CLI (`spawnSync`) for every query, and to `pg_dump` for backups. SQL is built with `?`/`@name` placeholders that get inlined via `escapeSqlLiteral` (not parameterized at the protocol level — the CLI is invoked with the final SQL string). This module also contains one-time legacy-SQLite-to-Postgres import logic (`readLegacySqliteDump`, gated to non-production, shells out to `python`). Requires the `psql`/`pg_dump` binaries on `PATH` (installed via `postgresql-client` in the Dockerfile).
2. **Editorial/content module** (`src/server/content/*`): a normal async `pg.Pool` (`postgres.ts`) against the same `DATABASE_URL`, scoped entirely to the PostgreSQL schema `editorial` (never touches the public/core tables). Migrations for this schema live in `db/migrations/*.sql` and are applied by `scripts/migrate-editorial.ts` / `npm run db:migrate:editorial`, not by the core module.

When adding a data access function, match the pattern of the module you're extending — don't introduce a `pg.Pool` call into `src/lib/database.ts` or a `psql` shell-out into `src/server/content/*`.

### Backend structure

- `server.ts` — single Fastify entrypoint. Registers `contentRoutes` (editorial module) as a plugin, then defines all core REST routes inline (auth, users, clients, daily-stats, integrations, ux-snapshots, rrss-channels, monthly-kpis, backups, dashboard summary). Auth is a bearer/session token checked per-route via `requireSession(req, reply, roles)`; there's no global auth middleware/hook. Serves the built SPA (`dist/`) and falls back to `index.html` for non-`/api` routes in non-test mode.
- `src/lib/database.ts` — core data layer (see above) plus session/user management, backups (`createDatabaseBackup`, writes to `INFIDASH_BACKUP_DIR`), and a Clarity (UX analytics) integration sync path called both from a route and from a background interval (`startClaritySyncScheduler`, skipped when `NODE_ENV=test`).
- **WooCommerce sales**: connection testing probes the read-only WooCommerce v3 orders API. An administrator can synchronize a bounded purchase-date window (31 days / at most 500 orders); complete snapshots are keyed by integration, HTTPS store identity and exact dates. Viewers can read that exact snapshot or request a transient preview. Only `completed` orders count; `total` already includes VAT and shipping; attribution is `date_created` in the store timezone; refund handling is client-configurable and applied when aggregating; currencies are never mixed. Snapshot persistence needs PostgreSQL tests before production use.
- **Lead capture**: WordPress integrations expose a rotatable bearer webhook URL for `POST /api/public/leads/:token`. Configure Fluent Forms or Contact Form 7 to send form submissions through WP Webhooks using POST. The receiver maps common Spanish/English contact fields, supports delivery idempotency when `infidash_provider`, `infidash_form_id`, and `infidash_delivery_id` are supplied, and enforces integration disable/rotation. Authenticated lead listing is paginated/filterable and does not return the raw payload. Do not infer conversion, CPL, or pipeline value without compatible source data.
- `src/lib/auth.ts`, `kpiThresholds.ts`, `integrationCatalog.ts`, `claritySync.ts` — supporting logic for password hashing/session tokens, per-client KPI threshold config, the catalog of supported integration providers/capabilities, and fetching Clarity UX snapshots.
- `src/server/content/` — the editorial module, structured as its own mini-service:
  - `contracts.ts` — shared validation/enum helpers and `ContentApiError`.
  - `repository.ts` / `apiRepository.ts` — data access against the `editorial` schema.
  - `routes.ts` — Fastify plugin exposing `/api/content/*`. Supports **two distinct auth modes** on the same routes: human sessions (`resolveHumanSession`, reusing the core session token from `src/lib/database.ts`) for the dashboard UI, and scoped **service tokens** (`serviceAuth.ts`, `authenticateServiceToken`) for n8n workflows — tokens are stored only as SHA-256 hashes in `editorial.service_tokens`, scoped per-client and per-capability (e.g. `jobs:claim`, `jobs:result`, `context:read`, `events:write`).
  - `migrations.ts` — the editorial migration runner (advisory lock, checksums, transactional).
  - `importContentHub.ts` — the legacy Content Hub importer used by `scripts/import-content-hub.ts`; requires an explicit ID-mapping file (never matches clients/accounts by name) and is idempotent via `editorial.legacy_mappings`.
  - `transitions.ts` — status transition rules for content jobs.
- `db/migrations/*.sql` — editorial schema only. Core-table schema is not migration-managed in this repo (see `src/lib/database.ts` bootstrapping).
- `workflows/content/*.json` — sanitized, disabled n8n workflow exports (dispatcher, plan/generate/publish per-client children, reconcile). These are documentation/reference artifacts, not executed by this repo. Job contracts are self-healing: Infidash re-reads `publications`/`publishing_accounts` server-side when a job is created or claimed rather than trusting client-submitted payloads. See `docs/content-workflows.md` and `docs/content-deployment.md` before changing job/lease/reconciliation semantics.

### Editorial/n8n pipeline: what has to be true for a job to actually run

Getting a job to go from "created in Infidash" to "n8n actually executes it" requires several independent pieces, set up in a system split across this repo, Postgres, and a separate n8n instance. The failure mode when any one piece is missing/wrong is almost always **silent** — the plan_item shows "Generando" and/or the job sits in `pending`/`running` forever, with no error surfaced in the Infidash UI. In rough order of what to check when a job seems stuck:

1. `editorial.client_settings` needs a row for the client with `enabled = TRUE` and a populated `workflow_bindings` JSONB (`{"generate_plan": "<n8n workflow id>", "generate_content": "...", "publish": "...", "reconcile": "..."}`). **There is no UI or API route to create/edit this row** — it's SQL-only by design (`docs/content-deployment.md` §3). `requireEnabledClient()` (`apiRepository.ts`) rejects job creation with 409 `EDITORIAL_DISABLED` if the row is missing or `enabled=false`; a missing/wrong entry in `workflow_bindings` makes the dispatcher's child-workflow lookup throw inside n8n with nothing reported back to Infidash.
2. `dispatcher.v1.json` must be **imported into n8n** (it is not deployed automatically by anything in this repo — it's a reference export) and its **Active toggle turned on** in the n8n editor. Without an active dispatcher, nothing ever polls `/api/internal/content/jobs/claim`, so jobs sit in `pending` indefinitely. n8n's own node inspector can display a stale `$workflow.active: false` even once the workflow is genuinely active and firing on schedule — trust the **Executions** tab's actual cadence over that field.
3. The dispatcher and child workflows pull secrets/config via `$env.*` expressions (`INFIDASH_INTERNAL_API_URL`, `INFIDASH_SERVICE_TOKEN`, `SERPAPI_API_KEY`, `JINA_API_KEY`, `OPENAI_API_KEY`, `GA4_PROPERTY_ID_INFICON`, `SERPROBOT_*`, `POSTIZ_*`, etc.) — these belong on the **n8n service/container's** environment, not on Infidash's own `.env`/`.env.local`. Easy to set on the wrong app when both run on the same host/platform (e.g. EasyPanel). n8n only picks up `$env.*` changes after a container restart, not a config save alone. Note `OPENAI_API_KEY` (a plain `httpHeaderAuth`-style REST call to `api.openai.com`) is distinct from the native n8n "OpenAi account" credential the `@n8n/n8n-nodes-langchain.lmChatOpenAi` nodes use elsewhere in these workflows — same provider, two separate auth mechanisms, both need to be configured independently.
4. `INFIDASH_SERVICE_TOKEN` (the n8n-side env var) must be the raw token whose SHA-256 hash (`serviceAuth.ts:hashServiceToken`) is what's stored in `editorial.service_tokens.token_hash` — generate a random token, hash it, insert the hash, and only ever put the raw token in n8n's env, never in the database or this repo.
5. `plan_item.status` flips to `generating` the instant `POST /api/content/jobs` succeeds (`apiRepository.ts`, inside `validateJobTarget`/`claimJob`) — **before** n8n has done anything at all. The UI showing "Generando" is not evidence the workflow is running; check `editorial.jobs.status` / `attempt_count` / `locked_until` / `last_error` for ground truth. There's no cancel/reset endpoint for `generate_plan`/`generate_content` jobs (unlike `publish`/`reschedule`/`cancel`/`reconcile` — see `contracts.ts` `isPublicationJob`); an item stuck in `generating` forever (job never reported back) can only be unstuck with a direct `UPDATE editorial.plan_items SET status='generation_failed', version=version+1, updated_at=now() WHERE id=...` — that reopens the "Generar contenido" button in the UI (`generation_failed` is an allowed source for `generate_content`).
6. `plan.v1.json`'s two heartbeat calls (`Heartbeat inicial`, right after claim, extends the lease by `leaseSeconds`; `Heartbeat tras IA`, right before saving results) must together cover the wall-clock time of the whole source-gathering + multi-agent synthesis pipeline. If that window is exceeded, `apiRepository.ts`'s `heartbeatJob`/`finishJob` return `409 LEASE_LOST "La reserva caducó o pertenece a otra ejecución"` and the job fails even though the plan actually finished generating (visible in `Parsear Plan JSON`'s own output) — it's a timing failure, not a data/API-key failure. `Heartbeat inicial`'s `leaseSeconds` is `2700` (as of 2026-09-21, bumped from `1200` after adding the JINA competitor-scraping branch made the pipeline slower); bump it further if this recurs as more source nodes are added.
   `LEASE_LOST` can also fire even when the *current* execution only took ~50s: `dispatcher.v1.json`'s initial claim (`Preparar reserva` → `Reservar siguiente trabajo`) only reserves `leaseSeconds` (`1800` as of 2026-09-21, bumped from `600`) before the dispatcher's own `Cargar binding del cliente` HTTP call to Infidash even runs, and only *after* that does `Renovar lease antes de ejecutar` extend it further. If Infidash is briefly unresponsive during that window (e.g. mid-restart — see the `psql`/event-loop-blocking tech debt above), the lease can expire and get reclaimed by the next `Cada minuto` tick with a fresh `lease_token`, orphaning the original in-flight execution — whose later heartbeat then reports "belongs to another execution" even though *it* ran fine. Check `editorial.jobs.attempt_count`/`execution_id` history on the job to confirm a double-claim happened.
7. `plan_item` transitions are strict (`transitions.ts`): `proposed → approved → generating → review → ready`. A `generate_content` job can't be created directly from `proposed` — the item must be approved first (`ContentTab.tsx` has an "Aprobar propuesta" button for this, only shown in `proposed`).
8. The `jsCode` strings embedded in `workflows/content/*.json` are not guaranteed bug-free just because they're a "sanitized export" — found and fixed a genuine missing-closing-brace syntax error in `plan.v1.json`'s "Validar trabajo" node (`Unexpected token ']'` at runtime). Treat these as real code to review/test, not inert config, when debugging a workflow failure.
9. A `generate_plan`/`generate_content` job that keeps failing (e.g. every dispatcher tick, once a minute) is not necessarily the *same* job racing itself — repeated manual retries (clicking "Generar plan" again after each fix) each create a **new** job row (`idempotency_key` includes a `:new:<timestamp>` suffix), so a backlog of several distinct `status='failed'` rows with `next_attempt_at<=now()` can accumulate and each get tried once per dispatcher tick, in `next_attempt_at` order — looking like one job endlessly retrying. Check `SELECT id,status,attempt_count,next_attempt_at,last_error FROM editorial.jobs WHERE client_id=... AND kind='generate_plan' ORDER BY updated_at DESC` before assuming a single stuck job; `claimJob` only reclaims rows with `attempt_count<8`, so `UPDATE editorial.jobs SET attempt_count=8 WHERE ...` freezes a backlog without needing a formal "cancelled" status. Every node that reports failure via `Preparar fallo confirmado` relies on `onError: continueErrorOutput` being set — `Heartbeat inicial` and `Heartbeat tras IA` didn't have it (as of pre-2026-09-21), so a `409 LEASE_LOST` there crashed the execution silently, without ever calling `Guardar fallo Infidash`, leaving the job's `last_error`/status stale and undiagnosable from the DB alone (only visible via n8n's own Executions list). Fixed by wiring both heartbeat nodes' error output to `Preparar fallo confirmado` like every other node in this workflow — though note a genuine lease loss will still fail at `Guardar fallo Infidash` too (by design: once the lease is gone, this execution has no right to write a result).
10. `editorial.publishing_accounts` needs one row per (client, provider) before `generate.v1.json`/`publish.v1.json` can run — same "SQL-only, no UI/API route to create it" pattern as `client_settings`/`workflow_bindings`. `Preparar contenido aprobado` (generate) and `Preparar publicacion` (publish) both throw `Cuenta WordPress/Postiz no autorizada para el cliente` if no `active=TRUE` row matches. The columns differ in how load-bearing they are: WordPress's `instance_key` is cosmetic (only used for the `sourceEventId`/event tracking key — the real WP connection is a separate n8n credential attached directly to the `WP INF Global` node), but Postiz's `external_account_id` is **functionally required** — it's sent verbatim as `integrationId` to the `n8n-nodes-postiz.postiz` node, so it must be the real channel ID from Postiz's own integrations list (e.g. a `cmt...`-prefixed id), not a made-up label. `id` is the table's primary key, so you can't reuse another account's id for a different provider — each needs its own fresh UUID, and any `editorial.publications.account_id` created before the right account existed (e.g. a publication scheduled when only a WordPress account was active, picked by default/mistake for what should've been a Postiz post) has to be `UPDATE`d separately to point at the new row. `platform` (`NOT NULL`, free text, no enum) is **not** the social network — for this client's real rows it's `'blog'` on both the WordPress and the GMB Postiz account, i.e. it identifies the content vertical/instance, not Facebook/Instagram/GMB. The social network Postiz actually needs to talk to a given account correctly (see #15) is only encoded in `instance_key` (e.g. `inficonglobal-gmb`) — when adding new Postiz accounts for other networks, give each one a distinct `instance_key` containing the network name (`inficonglobal-facebook`, `inficonglobal-instagram`), not a copy of an existing one, or the per-platform settings logic in `publish.v1.json` can't tell them apart.
11. Job payloads for `publish`/`reschedule`/`cancel` are "self-healing" only at the **moment of `claimJob`** (`apiRepository.ts` calls `publicationPayloadForJob` and persists the fresh payload into `editorial.jobs.payload` right there) — fixing `editorial.publications.account_id` (or any other publication field) does **not** retroactively update a job that's already claimed/running or whose `editorial.jobs.payload` was frozen on an earlier claim. The fix only takes effect on the *next* claim. Check `SELECT payload->'publication'->>'accountId' FROM editorial.jobs WHERE target_id=...` to see what a given job attempt actually has baked in versus what `editorial.publications.account_id` currently says — a mismatch means the job hasn't been reclaimed since the fix, not that the fix failed. Force an immediate retry (once the job is `pending`/`failed`, not `running`) with `UPDATE editorial.jobs SET next_attempt_at=now() WHERE target_id=...`.
12. `generate.v1.json`'s `Normalizar borrador y contenido` node used to hardcode `bodyText:null, excerpt:null` when saving generated content (as of pre-2026-09-22) — `applyContentResult` (`apiRepository.ts`) just passes these through verbatim, it doesn't derive anything. Since `ContentTab.tsx`'s "Programar publicación" form already defaults its `copy` field to `content.excerpt` (`copy: content.excerpt ?? ''`), a null excerpt silently became an empty Postiz `copy`, which only surfaces as `publish.v1.json`'s `Preparar publicacion` throwing `La publicacion requiere copy` — minutes later, in a different workflow, with no obvious link back to the missing excerpt. Fixed by deriving `bodyText` (HTML tags stripped, common entities decoded, whitespace collapsed) and `excerpt` (first 200 chars of `bodyText`, cut at a word boundary) from the humanizer's `bodyHtml` output in that same node. `PlanItem.keywords`/`.entities` (plural, feeding `generate.v1.json`'s content writer) had the same kind of gap — the brief form only ever exposed `keywordPrimary` (singular, used solely by `plan.v1.json`'s Google Trends node) even though the backend already accepted and persisted the plural fields; fixed by adding editable Keywords/Entidades inputs to the Brief form.
13. `publish.v1.json`'s `Preparar publicacion` requires an image (`requested.media?.[0]?.url ?? editorial_config.fallbackImageUrl`) before it will schedule a Postiz post — as of 2026-09-22, before that image ever existed anywhere in the pipeline, this always failed with `La publicacion requiere imagen o editorial_config.fallbackImageUrl` unless a client happened to have `fallbackImageUrl` set. Added an AI-generated header image ahead of `Preparar publicacion`: `Generar imagen IA` (raw `httpRequest` to `api.openai.com/v1/images/generations`, `gpt-image-1-mini`, prompt derived from `job.payload.publication.copy`) → `Convertir imagen a binario` (base64 → binary) → `Subir imagen a Postiz` (`n8n-nodes-postiz.postiz` `uploadFile`, returns a `path` Postiz can reference directly) → `Preparar publicacion`, which now tries the uploaded image's `path` first and falls through to `media`/`fallbackImageUrl` if generation failed. All three new nodes use `onError: continueErrorOutput` routed straight to `Preparar publicacion` so a flaky image call degrades to the fallback chain instead of failing the whole publish job; `Preparar publicacion` itself now reads `ctx` via `$('Cargar contexto Infidash')` instead of `$input.first()` since it's no longer `Cargar contexto Infidash`'s direct successor, and wraps the `$('Subir imagen a Postiz')` reference in try/catch since that node never executes at all on the error-bypass path. Reference pattern lifted from `docs/Blog Inficon global.json` (an untracked, unreviewed local file, not part of this repo) — that donor workflow's own `OpenAI - Generar Imagen Facebook` node had a dangling reference to a nonexistent `Preparar Imagen2` node, so only the four-node *pattern* was reusable, not the wiring verbatim.
14. `generate.v1.json`'s WordPress draft never got a featured/header image either (as of pre-2026-09-24) — `WP INF Global`'s `additionalFields` only set `content`/`status`. Added the same generate → convert → upload pattern as #13: `Generar imagen cabecera IA` (OpenAI images API) → `Convertir imagen cabecera a binario` → `Subir imagen a WordPress` → `Preparar imagen para WordPress` → `WP INF Global` → `Asignar imagen cabecera`. `Subir imagen a WordPress` is a raw `httpRequest` POST to `{siteUrl}/wp-json/wp/v2/media` (binary body, JPEG — `output_format: 'jpeg'` on the OpenAI call, explicit `Content-Type: image/jpeg` header) using `authentication: 'predefinedCredentialType'` + `nodeCredentialType: 'wordpressApi'` — this is the key trick: it lets a plain HTTP node authenticate with the *same* native WordPress credential already attached to `WP INF Global`, without creating a second Basic Auth credential per client. With ~30 clients each running their own copy of these workflow files, that avoids 30 duplicate secrets — after import, just attach the same existing WordPress credential to this node too, same one-time step as any other credentialed node here. `Preparar imagen para WordPress` converges both the happy path and every error-bypass edge (try/catch on `$('Subir imagen a WordPress')`, since that node never executes at all on an upstream error-bypass path) and defaults to `featuredMediaId: 0` (WordPress's "no featured image" value) if generation/upload failed, so a flaky image call degrades gracefully instead of blocking the WordPress draft.

    Setting the featured image is **not** done via `WP INF Global`'s (`n8n-nodes-base.wordpress`) own `additionalFields` — an earlier version of this workflow guessed at an `additionalFields.featuredMedia` key on that node, which is wrong and caused the job to fail downstream (surfaced as a generic "The service was not able to process your request" error, not on the WordPress node itself but on whichever node ran next, since the native node's declarative param builder silently drops unrecognized `additionalFields` keys instead of erroring — the post gets created, just without an image, and the failure only becomes visible once something later assumes the image was set). The correct pattern — create the post first (`WP INF Global`, unchanged, no image field), then a **separate follow-up call** — `Asignar imagen cabecera` (raw `httpRequest`, `predefinedCredentialType`/`wordpressApi`) — does `POST {siteUrl}/wp-json/wp/v2/posts/{{ $('WP INF Global').first().json.id }}` with JSON body `{"featured_media": <mediaId>}`; this is the standard WordPress REST API mechanism for setting a post's featured image, and matches an unused node (`Set Featured Image2`) found in one export of this agency's Thatsamore workflow. Note that node was never actually wired into that workflow's live connection graph (confirmed against the real, credentialed, `active:true` export) — Thatsamore's own production posts don't get a featured image set either, so this fix has no live counterpart to validate against, only the documented WordPress REST contract. This works for any `featuredMediaId` value including `0` (WordPress's "no image" sentinel), so it's safe to always call regardless of whether the upload succeeded. `Asignar imagen cabecera` has `onError: continueErrorOutput` with both outputs wired to `Heartbeat despues de WordPress` — if setting the featured image fails, the post (already created) still gets saved as a normal draft rather than failing the whole `generate_content` job over a cosmetic image problem. The site URL (`https://inficonglobal.es`) is hardcoded directly in both this node and the upload node, matching how every other node in this client-specific workflow file already assumes inficon-global — swap it if reusing this pattern for a different client's copy of the workflow.

15. `applyContentResult` (`apiRepository.ts`) used to look up an existing `editorial.contents` row by `id=item.contentId`, where `item.contentId` is set to `job.id` inside `generate.v1.json`'s `Normalizar borrador y contenido` node (as of pre-2026-09-24). Since every retry of "Generar contenido" for the same plan item creates a **new** job row with a fresh id (see #9), `item.contentId` was never stable across retries — the lookup by `id` always missed (no content row has that id yet), so it always fell into the `INSERT` branch, which collides with the table's `UNIQUE (client_id, plan_item_id)` constraint the moment a content row already exists for that plan item from an earlier successful/retried generation. That raw Postgres unique-violation isn't a `ContentApiError`, so it wasn't caught by any of the explicit error branches in `finishJob`/`applyContentResult` — it bubbled up as an uncaught exception and `routes.ts`'s generic `sendError` handler turned it into an opaque `500 {"error":"No se pudo completar la operación","code":"INTERNAL_ERROR"}`, reported by n8n's `Guardar resultado Infidash` node with no useful detail (the real stack trace only ever reached Infidash's own server logs via `console.error('[infidash] content api failed', ...)`, not n8n). Fixed by looking up the existing content row by `(client_id, plan_item_id)` instead — the column pair the `UNIQUE` constraint actually keys on — and reusing its `id` when found; `item.contentId` from the job payload is now only used as a fallback for the very first generation of a plan item, when no content row exists yet. This makes repeated `generate_content` retries against the same plan item correctly create new **revisions** of the same content row instead of colliding on a phantom duplicate insert.

    Separately, the header image generated in `generate.v1.json` (#14) is now threaded through to the Postiz publish job so the same image gets reused instead of generating (and paying for) a second one: `Preparar imagen para WordPress` also captures `headerImageUrl` from the WordPress media-upload response (`source_url`), which `Normalizar borrador y contenido` stores in `content.seo.headerImageUrl` (the same free-form `seo` JSONB slot already used for `keywords`/`entities`, no migration). `schedulePublication` (`apiRepository.ts`) defaults a new publication's `media` to that URL when the caller doesn't supply one explicitly, which flows into `editorial.publications.media` and is picked up automatically by the existing self-healing `publicationPayloadForJob` at both create and claim time. `publish.v1.json` gained an `Ya hay imagen reutilizable` IF node right after `Cargar contexto Infidash` that skips the whole `Generar imagen IA` → `Subir imagen a Postiz` chain when `job.payload.publication.media?.[0]?.url` is already set, and `Preparar publicacion`'s image priority was flipped so a reused image wins over a freshly-generated one.

16. `publish.v1.json`'s `Postiz1` node used to hardcode Google Business Profile's `settings.setting` array (`topicType`/`callToActionType`/`callToActionUrl`) unconditionally, regardless of which Postiz-connected network the publication's account actually pointed at — harmless while GMB was the only Postiz account configured, but wrong the moment Instagram/Facebook accounts get added (those require different Postiz setting keys entirely: `post_type` for Instagram, `__type` for Facebook, confirmed from real working nodes copied out of this agency's own n8n instance). Fixed by having `Preparar publicacion` build the settings array itself based on the account's network, and `Postiz1`'s `settings.setting` now references it via expression (`={{ $('Preparar publicacion').first().json.postizSettings }}`) instead of a fixed list. The network is detected from `account.instance_key` (see #10's warning about `platform` not being the network) via substring match (`'facebook'`/`'instagram'`/`'gmb'`/`'business'`/`'google'`) — case-insensitive, defaults to an empty settings array for anything unrecognized rather than guessing.

    Separately, `listPublishingAccounts` (`apiRepository.ts`) and `schedulePublication`'s account lookup were both narrowed to `provider='postiz'` — the "Programar publicación" dropdown in `ContentTab.tsx` was listing the client's WordPress `publishing_accounts` row alongside its Postiz ones (both `active=TRUE`), but selecting it always produced a job that failed instantly (`Preparar publicacion` requires `provider==='postiz'` and throws otherwise) since WordPress publishing isn't a "publish job" concept at all in this pipeline — it happens automatically as part of `generate_content` (see #14). The WordPress row itself is untouched (still required by `generate.v1.json`'s own account-authorization check); it's just no longer offered as a publish target through this UI/API path.

    This `instance_key`-vs-`platform` mixup recurred once already (2026-09-29): a follow-up edit to `Preparar publicacion` (adding `copyForPlatform`, an `imageId` field, and GMB URL validation) reintroduced `account.platform` for the network branch, silently breaking Instagram posts (Postiz rejected them with `posts.0.settings.post_type should not be null or undefined`, since `'blog'.includes('instagram')` is false and `postizSettings` fell through to `[]`). `tests/content-workflows.test.ts`'s Postiz-settings test had the same bug baked into its fixture (varying `platform` per case instead of `instance_key`), so it didn't catch the regression — fixed alongside the workflow code; the fixture now varies `instance_key` (`inficonglobal-<network>`) and holds `platform` fixed at `'blog'`, matching real data. Any future edit to this node's network-detection logic must key off `instance_key`, never `platform`.

**`editorial_config` wiring status:** `plan.v1.json`'s `⚙️ Configuración1` code node (not the old pre-sanitization `⚙️ Configuración` Set node) reads `topic`, `country`, `keywords`, `weeks_horizon`, `site_url` and (as of 2026-09-21) `competitors` from `Cargar contexto Infidash`'s `settings.editorial_config`, each with a hardcoded fallback so clients without that field still get static defaults. `keywords` falls back to `topic` (not `''`) when the client has no `editorial_config.keywords` — an empty `keywords` used to get sent as-is as the `q` query param to `🌍 D: Estacionalidad — SerpAPI1` (SerpApi `google_trends`), which rejects an empty `q` with `400 "Missing query \`q\` or \`category\` parameter"` and fails the whole plan job. Trends, the SerpAPI/Estacionalidad node, and both Search Console nodes already consume it via `$('⚙️ Configuración1')`. The competitor-analysis branch (`🏢 B: Scrape JINA Reader` / `🏢 B: Scrape JINA Reader2`, feeding `🏢 B: IA Analiza Competidor3` / `🏢 B: IA Analiza Competidor1`) scrapes `competitors[0]`/`competitors[1]` via JINA Reader (`https://r.jina.ai/<domain>`, auth via `$env.JINA_API_KEY`) — it was previously two Apify Instagram Scraper calls hardcoded to unrelated test accounts (`marketingcompass`/`limmaylimmon`); default fallback is now the real inficon-global competitors (`soyrafaramos.com`, `moodmarketing.es`). Rankings (`Datos serprobot 7 dias1`) now reads its `project_id` from `editorial_config.serprobotProjectId` (fallback `'4958413'`, the inficon-global project) — `SERPROBOT_API_URL`/`SERPROBOT_API_KEY` stay as `$env.*` since one SerpRobot account key covers every project. GA4 (`📊 C: GA4 — Top Contenidos1`) likewise reads `editorial_config.ga4PropertyId`, falling back to the old `$env.GA4_PROPERTY_ID_INFICON` (read inside `⚙️ Configuración1`'s own code, not the HTTP node) when a client has no per-client value yet. This split (account-wide secret in `$env`, per-client identifier in `editorial_config`) is the pattern to reuse for any multi-tenant integration; it doesn't scale to set one env var per client (this agency runs ~30 SerpRobot projects and presumably as many GA4 properties).

### Frontend structure

- `src/App.tsx` — top-level shell; renders `LoginScreen` until a session exists, then `Sidebar` + one of the per-domain tab components based on `activeTabId` from `useClientStore`.
- `src/store/useClientStore.ts` (Zustand) — session bootstrap/login/logout, client list, active client/tab selection; wraps `src/services/infidashApi.ts`.
- `src/store/useContentStore.ts` (Zustand) — editorial/content state; wraps `src/services/contentApi.ts`.
- `src/services/*.ts` — API clients (`infidashApi.ts`, `contentApi.ts`); `aiService.ts` is not the current Insights implementation. Insights are deterministic rules, not generated by a model.
- `src/components/*Tab.tsx` — one component per sidebar section (Overview, Sales, Traffic, Web, SEO, Leads, RRSS, AI Insights, Reports, Integrations); `src/components/content/` holds the Contenidos tab.
- Frontend imports use explicit `.js` extensions on relative paths even though the source is `.ts`/`.tsx` (ESM `moduleResolution: bundler` convention used throughout this repo) — follow this when adding imports.
- Path alias `@/*` maps to the repo root (`tsconfig.json`, `vite.config.ts`).

### Deployment

Single Docker image: `npm run build` (Vite) then `npm run start` (`tsx server.ts`) serves both the API and the built SPA from one Fastify process on `PORT`/`API_PORT` (default 3001 in the container, 4000 locally). The image installs `python3`, `make`, `g++`, and `postgresql-client` — the latter is required at runtime for `src/lib/database.ts`'s `psql`/`pg_dump` shell-outs, not just for the build.

## Notes

- Don't enable/activate the n8n workflows in `workflows/content/` without applying editorial migrations first and following `docs/content-deployment.md` — they write through `editorial` job contracts that assume the schema and service-token scopes already exist. See "Editorial/n8n pipeline" above for the full activation checklist.
- Service tokens for n8n are never read from an env var by the API; only their SHA-256 hash is persisted (`editorial.service_tokens`).
- **Known tech debt (not scheduled)**: `src/lib/database.ts`'s `psql`/`spawnSync` approach is a historical artifact (it replaced `better-sqlite3` before `pg` was ever added to the project — see commit `725f88b`), not a deliberate design choice. Migrating it to a `pg.Pool` like the editorial module would fix real issues (every query currently blocks Node's event loop, and SQL parameters are inlined/escaped manually instead of using real bind parameters) but touches ~1800 lines and nearly every route in `server.ts`, so it's deferred until explicitly prioritized. Don't "fix" this opportunistically inside an unrelated change.
  One narrow symptom of this *was* addressed (2026-09-22): `startClaritySyncScheduler()` (`server.ts`) used to call its first `psql`-backed sync (`listIntegrationsByProvider('clarity')`, via the blocking `spawnSync` layer) **synchronously right after `.listen()` resolves** — if that blocked the event loop long enough, the platform's own startup health check (`GET /api/health`) could time out and the orchestrator (e.g. EasyPanel) would send `SIGTERM`, killing an app that had just logged "API escuchando" moments earlier (`npm error signal SIGTERM` with no JS stack trace — the kill is external, not a crash). Fixed by delaying the *first* scheduler run by 10s via `setTimeout` so it doesn't compete with the critical post-boot health-check window; the recurring interval is unchanged. This doesn't touch the underlying `psql`/`spawnSync` architecture — if `SIGTERM`-after-boot recurs, check the platform's health check path/timeout/interval directly rather than assuming this specific fix covers every case.
